# تحديث إدارة المستخدمين والفرق في ENGHUB

## ملخص التنفيذ

أضيف إلى المشروع نموذجًا إداريًا جديدًا يعتمد على رقم الموظف وعلاقة `manager_id` الذاتية داخل جدول `users`. أصبح Top Manager قادرًا على إنشاء الحسابات يدويًا أو استيراد ملف Excel/CSV كامل، مع إنشاء الفرق أو إعادة استخدامها تلقائيًا، واستنتاج دور Manager للموظف الذي تتم الإشارة إلى رقمه أو اسمه كمدير، ثم تعيين بقية الصفوف التابعة له بدور Team Member.

أضيفت شاشة `/manager/team` للمدير. الشاشة تسمح بإنشاء أعضاء فريقه يدويًا أو استيراد ملف، ولا يقبل الخادم إلا الأعضاء المرتبطين بالمدير الحالي وبفريق يملكه. صفحة `/admin/users` ما زالت محمية لـTop Manager وتعرض رقم الموظف والمدير المباشر وتسمح بتعديل الحساب والدور والتفعيل وربط الفريق وإعادة تعيين كلمة المرور.

أصبح إرسال المشروع يحل المدير المباشر للمُرسل ويحفظه في `assets.manager_id` و`approvals.reviewer_id`. لا يظهر المشروع المعلّق في قائمة مدير آخر من نفس الفريق، ويستطيع المراجع المعيّن أو Top Manager فحص تفاصيل المشروع وفتح ملفاته عبر طلب موثّق، مع تسجيل فتح الملف في سجل التدقيق. يتم فك ضغط ZIP/RAR أثناء الرفع كما كان في النظام، لكن لا يتم تشغيل كود مرفوع تلقائيًا على الخادم، ولا توجد في النسخة الحالية آلية تشفير ملفات أو مفتاح فك تشفير يمكن تنفيذها بأمان.

## صيغة ملف الاستيراد

يجب أن يحتوي الصف الأول على الأعمدة التالية: `Employee Number`, `Full Name`, `Manager Number`, `Manager Name`, `user name`, `password`, و`Email Address`. العمود `Team Name` اختياري، لكنه موصى به عند استيراد أكثر من فريق. كلمات المرور مطلوبة بحد أدنى ثمانية أحرف، وتُحوّل إلى hash مع salt داخل الخادم ولا تُعاد إلى المتصفح.

بالنسبة لاستيراد المدير من صفحة الإدمن، يكفي أن يتكرر رقم الموظف في عمود `Manager Number` لدى الأعضاء التابعين له، أو أن يتكرر اسمه في عمود `Manager Name`. الصف الذي تتم الإشارة إليه يحصل على دور Manager، والصفوف الأخرى على دور Team Member. بالنسبة لاستيراد المدير من صفحة `/manager/team`، يجب أن تشير كل صفوف الملف إلى المدير الحالي برقم الموظف أو الاسم، ويُمنع إنشاء Managers من هذه الشاشة.

## تطبيق التحديث على الـVM

خذ نسخة احتياطية من قاعدة البيانات أولًا، ثم انسخ محتويات الملف المضغوط إلى نسخة المشروع الموجودة على الـVM مع الحفاظ على ملف البيئة السري وعدم رفعه إلى GitHub. بعد ذلك نفّذ:

```bash
cd /path/to/1enghub
pnpm install --frozen-lockfile
pnpm check
pnpm test
pnpm build
```

إذا كانت migrations السابقة تُطبّق يدويًا عبر `psql`، وبعد التأكد من عدم تطبيق التحديث سابقًا، نفّذ migration الجديدة مرة واحدة:

```bash
psql "$ENGHUB_DATABASE_URL" -f drizzle/0003_eager_shinobi_shaw.sql
```

إذا كانت قاعدة البيانات تُدار بالكامل عبر جدول migrations الخاص بـDrizzle، استخدم مسار Drizzle المعتاد بدل أمر `psql` اليدوي، ولا تطبّق الطريقتين معًا. تحقق من نجاح التحديث بالأمر:

```bash
psql "$ENGHUB_DATABASE_URL" -c "SELECT employee_number, manager_id FROM users LIMIT 1;"
```

ثم شغّل النسخة الإنتاجية بالطريقة المعتادة في الـVM:

```bash
NODE_ENV=production pnpm start
```

## التحقق الوظيفي المقترح

سجّل الدخول بحساب Top Manager، افتح `/admin/users`، نزّل القالب، وأدخل صف Manager وصف Team Member ثم ارفع الملف. تحقق من ظهور الحسابين ورقم الموظف والعلاقة المباشرة والفريق. بعد ذلك سجّل الدخول بالمدير، افتح `/manager/team`، وأنشئ عضوًا يدويًا أو ارفع ملفًا يشير إلى المدير الحالي؛ جرّب أيضًا ملفًا يشير إلى مدير آخر للتأكد من رفضه من الخادم.

أنشئ مشروعًا بحساب Team Member. يجب أن يذهب الطلب إلى المدير المباشر فقط. جرّب الدخول بمدير آخر من نفس الفريق، ويجب ألا يظهر الطلب في قائمة موافقاته. سجّل الدخول بالمدير المسؤول، افتح `Inspect project` لفحص الملفات، ثم وافق أو اطلب التعديلات أو ارفض. يجب أن يرى Top Manager الطلب كذلك، وأن يظهر فتح الملف في سجل التدقيق.

## نتيجة الاختبارات المحلية

نجح `pnpm check`، ونجحت 11 مجموعة اختبارات بإجمالي 28 اختبارًا، ونجح `pnpm build`. تم تشغيل نسخة التطوير ونسخة الإنتاج محليًا والاستجابة للصفحة الرئيسية بمعدل HTTP 200. لم أستطع الاتصال مباشرة بعنوان الـVM الخاص `192.168.7.70:3000` من بيئة العمل المعزولة، لذلك لا يمكنني تطبيق الملفات على ذلك العنوان أو اختبار بيانات PostgreSQL الحقيقية دون إتاحة الـVM/مسار المشروع داخل الجلسة.
